# 应用内更新下载与安装交接：技术设计

## 目标状态

用户在发现更新弹窗中明确点击“下载更新”后，当前弹窗立即转为同一更新操作的进度视图；下载完成后自动发起一次平台允许的安装交接。设置页的更新面板与该进度视图订阅同一 `UpdateManager` 状态，用户关闭进度视图后仍可在设置页查看或重试。

## 状态机

沿用 `UpdateManager` 作为唯一事实来源，并补齐两个约束：

- 一个 `UpdateInfo` 同时最多只有一个下载 Future；重复点击复用进行中的操作或显示其当前状态，绝不并行写同一安装包。
- 下载完成后的自动安装只由“用户已在弹窗确认下载”的操作链触发一次。手工从设置页下载仍可显示“立即安装”，但不应在未确认时自行下载。

建议将安装交接结果表达为可见状态，而非 Android 成功调用通道后立即回到 `idle`：

```text
available -> downloading -> downloaded -> handingOff
                                   |          |
                                 error     retryable downloaded
```

Windows 启动安装器后进入 `handingOff`；若进程启动失败或 UAC 未使应用退出，恢复为 `downloaded`。Android 调起系统包安装确认后显示“已打开系统安装确认”，保留 APK 和重新发起入口；未知来源权限缺失或调用失败也恢复为 `downloaded` 并给出动作提示。

## UI 与平台边界

- `showUpdateDialog` 的确认按钮不再 `pop` 后无反馈；它打开/转换为专用的下载进度视图，使用 `ValueListenableBuilder` 订阅现有状态、进度与错误。
- 下载视图允许用户返回应用，但不能重复启动下载；状态由设置页 `UpdatePanel` 复用展示。
- 将 Windows `Process.start` 和 Android `MethodChannel` 包装为可替换的平台安装启动器。生产实现保留当前通道名 `rch/updater`，测试注入 fake，不依赖真实 UAC 或 Android 系统 UI。
- 镜像候选、文件大小校验、失败后切换镜像和 GitHub Releases 兜底沿用现有 `UpdateManager` 逻辑。

## 安全与兼容性

- 不改变“稍后”或静默检查：它们绝不开始下载或安装。
- Android 仅请求系统安装确认，不能承诺或实现静默安装；Windows 仍由现有安装器/UAC 控制最终权限。
- 启动命令必须以参数列表传递安装包路径，避免临时目录中的特殊字符影响命令解释。
- 下载失败不删除已验证成功的安装包；仅失败的临时文件可按现有逻辑清理。

## 回滚

若新的进度视图或自动交接出现平台问题，回滚其入口即可恢复“下载后由设置页手动安装”的旧路径；镜像与下载校验模块不需要回滚。
