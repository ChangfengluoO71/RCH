# 网盘直连 vs OpenList 聚合：哪个更适合 RCH — 2026-08-03

> 用户问题：OpenList 只是参考，五个主流网盘（百度/夸克/阿里/115/PikPak）有没有更适合 RCH 的直接接入方法？

## 结论先行

**五家里只有百度、115 有明确的官方开放 API（且都要申请）；阿里云盘开放平台对个人不透明（实际主流做法是借用 AList 内置 client 扫码）；夸克、PikPak 完全没有官方 API，只能 Cookie/逆向。**

因此"逐网盘官方 API 直连"这条路**覆盖不全、门槛高、维护成本是聚合方案的数倍**，不是更优路径。**OpenList/AList 通用 API 书源（方案 A）依然是性价比最高的选择**：一个客户端覆盖全部网盘，把夸克/PikPak 的逆向维护、各家的风控/接口变动成本转移给 OpenList 社区。

## 1. 五家直连可行性总表

| 网盘 | 官方开放 API | 申请门槛 | RCH 直连工作量 | 主要风险/坑 |
|---|---|---|---|---|
| 百度网盘 | 有（百度网盘开放平台 union） | 个人实名 + 创建应用 + 勾选"网盘基础服务"权限 + 审核 | 中（≈1 个 SFTP 书源） | >20MB 下载须带 `User-Agent: pan.baidu.com`；速度受 SVIP 限制；权限审核可能被拒 |
| 夸克网盘 | **无**（只有网页内部接口） | —（无官方入口） | 大（逆向 drive-pc.quark.cn，Cookie 登录） | Cookie 易失效、账号风控、接口随时变动、封号风险 |
| 阿里云盘 | 有（阿里云盘 Open，官方授权 API） | 开放平台对个人申请不透明；主流做法是借用 AList 内置 client 扫码 | 中 | 必须移动端来源 token；referer 限制；借内置 client 合规性存疑；禁止公开分享否则冻结 |
| 115 | 有（115生活 OpenAPI，内测申请制） | 填申请表（应用类型/接口/预计用户量/调用次数），审核制 | 中 | 同一账号同一应用仅 2 个有效 refresh token；禁止图床/软件床/共享账号/代 OSS 等场景 |
| PikPak | **无**（社区逆向 SDK 才可用） | —（无官方入口） | 大（逆向 + OAuth 模拟） | 国内禁止访问需代理；直链绑定请求 IP；逆向接口变动风险 |

## 2. 各家详情

### 百度网盘 — 有官方 API，可直连
- 开放平台：pan.baidu.com/union，个人实名认证即可创建应用，OAuth2 授权，勾选"网盘基础服务"权限（文件列表/上传/下载）。
- 下载：官方签名直链，但 >20MB 文件必须带 `User-Agent: pan.baidu.com` 请求头；速度与 SVIP 等级挂钩。
- 结论：技术上可行；审核 + 应用合规 + 下载限速是现实负担，且只覆盖这一家。

### 夸克网盘 — 无官方 API，只能逆向
- 官方无任何开放文档/入口；社区方案全部基于网页内部接口（drive-pc.quark.cn / pan.quark.cn）+ Cookie。
- 直连意味着 RCH 自己维护逆向逻辑：Cookie 抓取、风控对抗、接口变动跟进，账号有封禁风险。
- 结论：**不适合 RCH 直连**，必须依赖聚合层（OpenList/AList）把这块脏活包掉。

### 阿里云盘 — 官方 API 存在但对个人不透明
- 官方 Open API 存在（阿里云盘开放平台），AList 的"阿里云盘 Open"驱动即基于它。
- 但开放平台面向企业/内测，个人开发者申请路径不透明；社区 aligo 等 SDK 均通过内置 client + 扫码获取 refresh token（即借用 AList/第三方 client 凭据，合规性存疑）。
- 直链约束：必须移动端来源 token（referer 限制），桌面 Web token 直连下载会失败。
- 结论：直连可行但授权路径绕（自己申请没门路，借别人的不合规）；聚合层方案直接规避。

### 115 — 有官方 OpenAPI（内测申请制）
- 115生活开放平台已开放个人云存储能力（2025 年内测），AList 已适配 `115_open` 驱动：手机扫码获取 refresh token，一个账号同一应用只能持有 2 个有效 token，第三次获取顶掉第一次。
- 申请制：需填应用类型/名称/描述/相关接口/预计用户量/每日调用次数；禁止图床、软件床、外链视频播放、共享开发者账号、替代 OSS 等场景。
- 对 RCH：场景（个人漫画文件管理/阅读）符合平台定位，但**需要申请且审核不确定**；若 RCH 内置一个共享 APP ID 给所有用户扫码（AList 做法），触碰"开发者账号共享"红线。
- 结论：可直连，但申请 + 合规 + token 数量限制，性价比低于聚合层。

### PikPak — 无官方 API，只能逆向，且国内访问受限
- 官方无开放平台；社区 SDK（pikpak-js-sdk / pikpak-go 等）基于非官方接口 user.mypikpak.net。
- 个人盘直链绑定请求出口 IP（"谁发出请求谁能用"），且国内网络无法直连（需要代理）。
- 结论：**不适合 RCH 直连**；即便做，对国内用户意义有限。

## 3. 方案对比

| 方案 | 覆盖 | 工作量 | 维护成本 | 风险 | 用户侧成本 |
|---|---|---|---|---|---|
| A. OpenList/AList API 书源（推荐） | 40+ 网盘一次覆盖（含夸克/PikPak/115 分享等） | ≈ SFTP（1 个 HTTP 客户端） | 低（HTTP API 面稳定，逆向由社区承担） | 低（用户自建自用，无共享合规问题） | 需自建 OpenList（单文件/容器，约 1 分钟） |
| B. 逐网盘官方 API 直连 | 百度 ✓ 115 ✓ 阿里 △ 夸克 ✗ PikPak ✗ | 3~5 个驱动，每个 ≈ SFTP 量级 | 高（接口变动 × N，各家风控/审核跟进） | 中高（应用审核被拒、token 限制、借用 client 合规） | 每家单独授权一次 |
| C. 混合（官方直连 + OpenList 补齐） | 全覆盖 | 4~6 个驱动 | 最高（两套体系） | 中 | 部分网盘自建 OpenList + 部分单独授权 |
| D. 零开发（CloudDrive2 / 官方客户端 / WebDAV） | 取决于用户工具 | 0 | 0 | 0 | 用户自己挂载后走 RCH 本地/WebDAV 书源（用户已能自理） |

## 4. 建议

1. **主推方案 A（OpenList/AList 通用书源）**：一个 Rust HTTP 客户端 + 三态打开策略 + raw 缓存，复用 WebDAV/SFTP 的整套书源框架。夸克/PikPak 这种无官方 API 的网盘，只有这一条路能"原生"覆盖。
2. **不推荐逐网盘官方直连**：覆盖不全（夸克/PikPak 直接没戏）、申请/合规/维护成本高；等 OpenList 聚合层跑顺了，若用户反馈强烈再评估单独直连百度/115（列为远期 R2）。
3. **添加书源对话框按"网盘类型"切换凭证输入**（token / Cookie / 账号密码），内嵌各家获取指引——无论走聚合还是官方直连，这层 UI 都复用。
4. 下载链路设计不变：raw_url 直链 + auto 整本下载（失败回退 Range 流式）+ 百度场景请求头自动带 UA。夸克直链不稳时，auto/download 优先，stream 兜底。
