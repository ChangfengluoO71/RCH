# 设计草案：115 云下载、Android Daily 与平板模式

日期：2026-10-28 至 2026-10-29。方案仅供评审，未修改业务代码。与现有 EH→115 任务共享上下文，但不改写历史调查记录。

## 1. 115：把“上传种子”和“创建 BT 任务”分别建模

### 现状与诊断

当前 Cookie 路线刻意先把 Torrent 上传到所选目标目录，之后按种子文件 SHA-1 请求远端解析，再按 Infohash、文件索引及目标目录向 SSP 提交 BT。这个中间上传本身可以是接口要求；用户看到目录里出现 Torrent 并不能证明云下载任务已创建。流程、分叉和已知问题：

1. `Cloud115BtBatchProcessor` 在 `PARSED` 之后才会走 `submit`；`UPLOADED_PARSE_PENDING`、上传结果未知、解析不一致或空文件列表均会跳过提交。`app/lib/store/cloud115_bt_batch.dart:918`、`:989`、`:1081`。
2. `parse_remote_torrent_parse` 只接收 Web 响应的 `torrent_filelist_web` 或 `files`，并逐项对比路径、大小、顺序；`finish_uploaded_torrent` 的异常在普通 OSS 上传成功路径会归并为待解析，隐藏具体原因。复用已有上传或秒传的路径则可能以另一种未知状态暴露异常。`app/rust/src/source/cloud115_offline.rs:350`、`:939`、`:1039`。
3. SSP 提交仅根据 `state` 的布尔值分类，显式拒绝时没有保留可识别的业务错误码；所以当前不能区分权限、额度、参数或协议变化。`app/rust/src/source/cloud115_offline.rs:1107`。
4. 在目前的汇总器中，全部 `rejected` 可以被计入 `skipped`，但 `complete` 不检查该值，运行摘要可能显得比实际结果乐观。`app/lib/store/cloud115_bt_daily_workflow.dart:185`。
5. Flutter 的 `cloud_stage` 会在经由 Rust 的 `EhAutomationRun` 反序列化/序列化时丢失；`partial` 也不被 Rust 终态允许。手动扫描先记录 completed，面板随后再写云阶段终态时现有状态机不允许从已完成状态再次终结。`app/rust/src/eh_subscription.rs:138`、`:1702`、`app/lib/store/eh_subscription_store.dart:1074`、`app/lib/ui/eh_subscription_panel.dart:438`。
6. 目标目录在提交前被校验并通过 `wp_path_id` 发送，`savepath` 为空；但 `read_task_status` 找到同 Infohash 后把请求的 `target_folder_id` 原样放进返回值，没有从远端任务验证该目录。`bt_delete_local_torrent_if_remote_task_found` 因而可能在只有其他目录同哈希任务时删除本地种子。现有 mock 的任务行不包含目标目录，删除测试仍通过，证明该测试没有覆盖目标目录证据。`app/rust/src/source/cloud115_offline.rs:660`、`:1148`、`:1391`、`:1792`、`:2739`、`:3763`。

本次没有读取用户 Cookie、连接真实账户或发送 115 请求；只凭代码无法确定用户此次具体卡在解析、提交拒绝、会话或其他阶段。不能把上述可达缺陷当成已复现的唯一根因。

### 路线比较

| 路线 | 优势 | 限制 |
| --- | --- | --- |
| 本地解析后直接提交 Cookie BT 任务 | 现有预检可给出 Infohash 和文件索引，现有 BT 提交函数不依赖上传结果；可避免在目标目录存放 `.torrent` | 115 是否仅凭 Infohash 得到元数据、是否接受本地文件索引、能否下载 EH 资源尚未实测；依赖 115 元数据缓存或网络获取能力 |
| 修复现有 Cookie Web 路线 | 沿用现有书源、选择器、批处理和账本，最直接服务已有配置 | 实际 Web 协议和业务错误需要对照最新材料及脱敏实测；不可把 mock 当线上契约 |
| 新增独立 OAuth 开放平台路线 | 协议边界和授权更清晰；第三方 SDK 有种子解析与 BT 提交模型 | 端点详细官方页面本次不可访问，权限/账号可用性待确认；不能拿 Cookie 调 Open API，也不能静默换账户 |
| 把 Torrent 转磁力链接提交 | 可直接创建链接云下载任务，无需先上传 Torrent | 可按规范附带 Tracker，但 115 是否采用这些参数尚未验证；只用 Infohash 可能无法获取元数据，文件选择能力也与 BT 接口不同 |

根据用户希望直接调用 115 的后续问题，建议优先验证“本地读取 Infohash → 直接 Cookie BT 提交”的候选路线，保持当前账户及账本语义；以一个实际种子验证服务器能否解析、文件索引是否对应、任务是否真正下载。115 如果明确不支持，再评估磁力或原始种子上传解析路线；结果未知时禁止盲目切换路线重复提交。直接提交 Infohash 不等于把完整 `.torrent` 内容直接传给 115，不能保证 Tracker 或其他元数据随之传递。将上传、解析、提交、查询抽象为清晰的适配器边界。确认官方开放能力与权限后，可独立增加 Open API 适配器，只有用户明确选择对应授权书源时使用。若 Open API 不可用，不宣称其已支持。

### 接口与状态契约

- 文件整体 SHA-1 用于上传和远端种子定位；BT v1 Infohash 是原始 bencoded `info` 字典的 SHA-1，二者不可混用。对于第三方 SDK 的 Open API 实现，解析需要 `torrent_sha1`、`pick_code`，提交模型还包含 `info_hash`、`wanted`、`save_path`、`wp_path_id`；这不等于已核实官方授权。Web Cookie 的解析和提交协议与 Open API 分开建模。
- 保持每项清晰可恢复的状态：`validated`、`upload_started`、`uploaded`、`parse_pending`、`parsed`、`submit_started`、`accepted`、`remote_duplicate`、`downloading`、`completed`、`rejected`、`unknown`。兼容映射现有 JSONL 状态，不清空账本。`accepted` 指请求受理；`completed` 仅在相应任务完成证据明确后出现；目标内容和 RCH 读取再单独显示。
- 增加受限的结构化诊断：阶段、HTTP 状态、已核实的业务码、解析失败类别、重试建议；不保存 Cookie、令牌、原始响应、完整下载链接或私有文件名。按真实响应验证后再支持新的字段/顺序/路径表达，不能仅因为 Open SDK 字段名不同就直接用于 Cookie 接口。
- 区分 `not_sent` 与 `possibly_sent`：前者可在可重试条件恢复；后者只读核对，未知时不重发。已有同哈希远端任务只按可证明的账号、目标和任务证据认定；受限分页不能证明不存在。
- 修复 Dart/Rust `EhDailyRunRecord` 对应持久化 schema，增设向后兼容的云阶段和 `partial`，并以 run ID 或条件更新表达完整工作流生命周期，避免手动 EH 扫描先终结、云阶段二次覆盖失败。所有成功、拒绝、未知、取消均在重启后可读。
- 默认保留上传到 115 的 Torrent 和本地 Torrent；已有显式本地清理设置只在现有验证条件满足后执行。远端中间文件可否使用单独目录或清理列为后续可选项，不默默删除。
- 直接 BT 候选应在现有批处理的预检后使用本地 `files` 构造 `wanted`，复用提交前持久账本，不把未核实的文件索引映射当作已确认；先实测所有文件和多文件选择。仅当 115 明确拒绝且能确认未创建任务，才可由用户或已定义策略选择上传解析备选；对超时或不确定结果先只读核对。
- 将现有 115 目标目录选择绑定到直接提交：传递该目录 ID，不以本地 Torrent 保存目录替代。通过已验证的任务字段或目标文件夹内容，独立确认实际远端目录；若 Cookie 接口不返回可信目录证据，显示“目录待核对”并保留本地种子。实际任务可能在所选目录下创建子文件夹，精确目录结构需实测。

## 2. Android Daily：前台和系统后台共用同一轮工作

### 方案选择

仅开放当前进程内 Timer 最省事，但应用被系统回收或关闭后不会自动执行；不满足通常意义上的手机后台每日工作流。建议使用 Android WorkManager 持久调度，加上前台启动/恢复时的同一资格检查。它是尽力而为，不保证固定时刻：Doze、后台配额、断网、电池优化、关机及强行停止均可能延迟或阻止执行。建议每 6 小时检查资格，按本地日期领取最多一轮新运行，避免把 24 小时间隔误认为每天固定时刻；不回补过去多天。

### 边界与生命周期

1. 用户开启后登记唯一周期工作；关闭时撤销未来调度，并安全处理已运行任务。App 启动/恢复和 Worker 共享同一个运行服务，不各自编排一套。
2. Worker 启动 headless Flutter 执行环境或原生桥接，显式初始化所需插件、Rust/FRB、持久化路径、EH 配置及唯一 115 书源；不得调用依赖 Widget 的对话框，也不得用只属于前台 isolate 的单例或内存会话。复用前台的无 UI 启动逻辑，先按 marker/library.json 恢复自定义缓存根，再打开数据库和加载书源（`app/lib/main.dart:54`）；否则后台可能打开默认空库。Android 凭据和存储 MethodChannel 当前只在 `MainActivity.configureFlutterEngine` 注册：要将后台所需的非交互通道提取为可给 headless engine 注册的插件/桥接。`CredentialVault` 的实例级 `@Synchronized` 和共用 `.part` 文件不足以保护多实例，需为跨引擎/进程的凭据及书源读改写设计真正串行化、原子更新和冲突处理；现有 Dart single-flight map 也只属于一个 isolate。无法在后台取得或安全恢复凭据时显示“等待认证”，不悄悄创建新登录或无限刷新。
3. 用户选定的本地种子目录必须在冷启动和后台仍可读写；核对 Android 的文件路径与授权机制，失效则停止并提示重新选择，不能假定桌面路径或交互式选择器在后台可用。
4. 调整 `try_acquire_collection_lock` 的非 Windows 空实现：前台手动、自动和后台持有同一可跨 isolate/进程的运行 lease；领取、停止、恢复、账本都要以持久状态和真正的锁协调。锁持有期间不能把活任务恢复为中断；进程死亡释放锁后才恢复。具体文件锁/SQLite 事务方案需在 Android 真机验证，不能只依赖 Dart isolate 内的 map。
5. 一次本地日期产生一个 run ID。按阶段保存可验证检查点；重复唤醒/系统重试只恢复同一轮，不新建第二轮。当前只有一个会被手动运行覆盖的 `last_run` 槽（`eh_subscription.rs:120`、`:1742`），因此需要独立持久保存当日自动 run ID/检查点与最近手动结果，或按 run ID 存储和索引；读取旧配置时向后兼容。等待认证/网络后即使执行手动任务，冷启动仍能找到原自动运行。扫描的断点恢复需明确实现或通过现有 manifest 去重后重扫；115 账本的“写入可能已发送”绝不自动重放。即使同一天认证或网络暂不可用，也可以在安全的未写入阶段有限重试，而不是先消耗当天资格后永远等待次日。
6. EH 扫描可能超过普通 Worker 时间限制。优先分段、保存检查点并让系统重调；确需长运行时，按当前 Android 版本处理可见前台通知、服务类型、启动限制和配额。不能承诺绕过系统限制。运行前持久化阶段及写入意图；系统杀进程时不能假定执行收尾，下次启动确认 lease 已释放后再标记中断并安全恢复。
7. UI 显示启用状态、运行阶段、最近日期、下一次“等待系统调度”、等待原因和可手动重试的安全操作；开启前提示后台运行受系统限制。显式失败/未知不能显示“全部成功”。

## 3. 平板模式：设备体验与窗口宽度解耦

### 布局

- `tabletLayout` 增加 `tablet`，继续识别旧 `auto`、`desktop`、`mobile`，不把旧 `desktop` 直接重写为新值。建议 Android 大屏 `auto` 有效解析为平板体验，但初始导航结构与当前大屏保持一致；用户手动 `desktop` / `mobile` 的语义保留。
- 引入一个解析函数统一计算“所选模式”和“实际紧凑程度”；它们是不同概念。平板分屏或窄窗口可临时用紧凑导航，却仍记住平板模式。允许用户在 Android 设备上手选平板，避免仅靠 600dp 猜测物理设备。
- 方向策略独立于 `isCompact`：用户选择平板或自动识别为平板时，即使临时窄窗口也不因紧凑导航强制竖屏；普通手机仍维持现有策略。统一处理首页及阅读器（`reader_page.dart:298`、`:2134`）的方向设置，避免阅读器退出时按打开瞬间缓存的紧凑状态覆盖当前模式。横竖屏、窗口尺寸和设置切换要及时重新计算。

### 材质

- Windows `windowMaterial=standard/mica` 是原生 DWM，不能直接在 Android 使用。现有 Flutter 弹窗模糊受 `defaultTargetPlatform == windows && micaSupported` 限制；需把材质能力从“Windows 云母是否支持”中拆出。
- 为 Android 平板新增独立的本机材质设置：标准与 Flutter 实现的局部磨砂/半透明弹窗（可另加轻量静态表面效果）。效果依赖应用内部的背景，不能声称是 Windows 的系统云母，也不承诺模糊系统桌面。保留 Windows 设置键和原有功能，避免不同平台相互覆盖。
- 模糊只用于裁剪范围内的应用弹窗/面板，不作用于漫画封面和阅读画布；高对比度、能力不足或低性能场景回退标准。默认标准，展示效果预览和文字可读性，具体视觉强度及低性能判断在实机验收时确定。

## 4. 依赖与风险

- 先完成 115 实际阶段诊断及状态持久化，才能让 Android Daily 正确报告和恢复；平板模式可独立实现，但最终需一起验收。
- 115 任务是否完成、目标文件是否出现、RCH 是否能读是三项不同结果。真实服务与访问凭据不可用时只报告未验证。
- 不能根据当前工作树的代码版本推断用户设备安装版本；实测需核对版本和构建。
- 不恢复已移除的历史 P0 代码级门禁；本次建议的真实服务核对是验收条件，不改变用户此前对产品行为的授权。
