# 后台任务与前台响应优化方案

**状态：** 方案 B 修订已通过，已开始执行。阶段 3 的 isolate 改造仍暂不批准，只有阶段 0–2 的性能证据仍表明需要时，才单独提交审阅。

**日期：** 2026-10-12

## 1. 背景与目标

应用会在后台执行书源扫描、同步、目录索引刷新、抓取和批量操作。用户反馈，在书源扫描、同步或批量操作期间，前台操作有时会变慢；添加夸克、115 等云端书源时，扫码、Cookie 验证或连接也需要等待。本方案希望减少任务对页面交互的影响，并让等待过程有明确反馈，同时保证后台任务最终完成、索引和标签数据不丢失。

优化按证据分阶段推进：先消除可确认的重复工作和过多数据库往返，再测量剩余卡顿来自 Dart 主 isolate、文件系统、数据库锁还是图像处理，只有测量证明有必要时才引入 isolate 或更复杂的调度机制。

## 2. 已确认的代码情况

以下是当前代码结构的观察结果，不是对用户设备上每次卡顿来源的最终归因。

### 2.1 自动化任务会定时运行，也会被宽泛的状态变更触发

- `app/lib/store/automation_coordinator.dart` 中的自动化轮询间隔为 60 秒，初始化时会立即启动一次 `startup` 周期。
- 自动化协调器监听整个 `LibraryStore`。任意 `LibraryStore.notifyListeners()` 都会触发约 2 秒防抖后的维护周期，而不只是在书库目录确实变化时触发。
- 一个维护周期会刷新目录快照；同步后重新加载书库，又会再刷新一次目录快照，之后还可能执行清理、抓取和物化任务。快速轮询即使因远端 revision 未变而没有真正同步，也仍会进入协调器后续的本地快照处理。
- 当前 `markDirty()` 在 `_running` 时直接返回，`runCycle()` 在周期已运行时也直接返回上次结果。因此，周期运行期间发生的真实目录变更或新触发意图可能被丢弃；这不仅是重复工作问题，也是正确性问题。
- 同时，监听整个 `LibraryStore` 会让收藏、阅读进度等不相关通知触发维护。修订方案需同时做到“只接收相关变更”和“运行期间保留 pending dirty 意图”。

参考：`app/lib/store/automation_coordinator.dart`，`app/lib/store/sync_engine.dart`。

### 2.2 本地目录扫描包含递归遍历和元数据哈希；主 isolate 瓶颈尚未证实

- `LibraryIndexService.scanLocalSource` 会递归遍历本地目录、读取文件系统元数据，并构造索引条目。`libraryIndexId` 的 SHA-256 输入是 fingerprint 与规范化路径；`entryHashOf` 的 SHA-256 输入是路径、名称、条目类型、大小、修改时间和 asset 类型。
- 这些哈希是路径/元数据标识，不是漫画文件内容哈希；当前代码没有显示扫描器会为了计算该 SHA-256 读取整本漫画文件。
- 当前扫描流程在 Dart 异步调用路径中运行，尚未看到将遍历与结果组装放入独立 isolate 的实现。但仅凭这一点不能认定它造成帧卡顿。
- 扫描结果会汇集后写入 Rust/SQLite 索引。
- 增量扫描遇到 mtime 未变的子树时，会遍历 `previous` 集合并逐条做路径前缀判断，以保留旧条目。若基线证明这段重复筛选占用明显 CPU/分配成本，应先评估按目录预分组或按路径有序索引，减少重复扫描旧条目，再讨论 isolate。
- 文件系统 I/O、目录项数量、对象分配、路径处理和数据库等待都可能影响总耗时；各自占比应由 Profile 数据验证。

参考：`app/lib/store/library_index_service.dart`，尤其是 `scanLocalSource`、`refreshSourceIndex`。

### 2.3 SQLite 访问共享一个全局连接锁

- Rust 数据库层使用一个全局 `Mutex<Connection>`。不同功能的查询和写入会依次等待这把锁。
- 长时间或高频的数据库操作可能增加前台查询、保存操作的等待时间。
- 项目数据库规范要求批量写入使用单个事务；事务中只做 SQL，不在持锁期间执行文件系统或网络 I/O。

参考：`app/rust/src/db/mod.rs`；规范：`.trellis/spec/backend/database-guidelines.md`。

### 2.4 批量标签包含未等待索引、逐项关联持久化和吞错保存路径

- `LibraryStore.batchTag` 当前返回 `void`，逐目标调用异步的 `ensureIndexed()` 时没有等待其 Future；内存标签更新后调用 `saveToDisk()`，自身也未等待保存完成。
- `TagRepository.link()` 每新增一条关联都会通知监听者。批量标签虽在最后另行通知 `LibraryStore`，但标签仓库的逐项通知仍会发生。
- `TagRepository.saveToSqlite()` 不只是写入关联：它会确保标签、加载 SQLite 中的全部关联、计算差异，然后逐条调用 unlink/link API。故仅将 `ensureIndexed()` 改为批量 FFI，不能证明标签持久化往返已经批量化。
- `LibraryStore.saveToDisk()` 的 Future 完成不等于保存成功：SQLite 错误会被捕获并记录到 `lastSaveError`，JSON 备份也按 best-effort 处理。因此新的批量操作需要明确取得本次保存结果，不能仅依据 Future 正常结束报告成功。
- 代码库已有 `dbEnsureIndexEntries` 批量接口，它能在一个事务中处理多条索引记录并确保父路径链；快照索引流程已经使用这一接口。
- 该索引接口一次事务处理整批条目；对很大的批次，仍需测量并限制单次持锁时间，可按有界批次提交并在批次间让出调度机会。批量目标仍需保留文件与目录的条目类型、名称和父路径语义。

参考：`app/lib/store/library_store.dart` 中的 `batchTag`；`app/lib/store/library_index_service.dart` 中的 `ensureIndexed`、`indexDirSnapshot`；`app/lib/repository/tag_repository.dart` 中的 `link`；`app/lib/src/rust/api/db.dart`；`app/rust/src/api/db.rs` 中的 `dbEnsureIndexEntries`。

### 2.5 可见图片加载已有并发上限

- 封面队列和阅读器页面加载目前分别限制了并发数。
- 所以不建议不经测量就统一降低所有并发数；这可能让阅读和浏览本身变慢，而未解决扫描或数据库锁竞争。

参考：`app/lib/ui/comic_cover.dart`，`app/lib/ui/reader_page.dart`。

## 3. 设计原则

1. **前台意图优先。** 用户正在打开书源、阅读、同步或批量编辑时，自动维护任务让出资源；后台工作延后后仍能恢复。
2. **合并重复工作，不丢任务或变更意图。** 同源重复索引请求可以合并；强制重建不能被普通刷新悄悄替代；周期运行期间出现的 dirty 意图必须排队并在当前周期后重新核对。
3. **先减少不必要工作。** 在引入线程/isolate 或复杂优先级队列之前，先移除重复刷新和逐项数据库调用。
4. **数据库事务短且纯。** 遍历文件和网络同步在事务外；数据库锁内只进行必要 SQL。批量写入需在减少往返与限制单次锁持有时长之间取平衡。
5. **保留既有行为语义。** 不改变远端扫描判定、标签目标的文件/目录类型、索引原子发布语义和用户触发的强制刷新结果。
6. **以设备测量决定后续投入。** Android 手机端和 Windows 桌面端分别记录帧时间、阶段耗时与数据库等待，避免用桌面数据替代手机结论。
7. **保持独立自动化契约。** H1 EH Daily 与 115 自动化不纳入本轮调度改造；不得改变其每日领取、跨进程去重、状态持久化或 115 连接/扫描流程。

## 4. 推荐方案：分阶段实施

### 阶段 0：建立基线和定位工具

在优化前记录少量、能直接回答问题的指标。性能结论使用 Flutter Profile 模式（耗时对比可补充 Release 模式）；Debug 模式帧耗时不作为性能结论。避免先铺设覆盖所有数据库调用的重型埋点。

**记录内容**

- 前台：Flutter `FrameTiming` 中 build/raster 耗时分布、p95 和超过设备帧预算的帧数量；60 Hz 可参考 16.7 ms，高刷新率设备按实际刷新率解释预算。
- 扫描：源数量、目录/文件条目数、目录遍历及 stat 耗时、元数据/路径处理耗时、结果组装耗时、索引写入耗时；特别拆出未变化子树从 `previous` 筛选旧条目的成本。
- 同步：远端 revision 检查、完整同步请求耗时、应用到本地的数据域/条目数，以及同步前后快照刷新次数和耗时。分别记录本地目录 dirty 与远端同步应用变化，不能把二者合并为一个“有无变化”。
- 批量标签：目标数、逐项/批量索引 FFI 调用数、标签关联读写调用数、每批持锁时长、总耗时，以及批量期间帧耗时。
- 云端书源连接：从点击添加/连接到扫码或 Cookie 提交、验证、会话建立及首个目录可用的各阶段耗时；确认等待动画是否及时出现、是否因重复点击发起了重复连接。
- 数据库：仅在上述重点路径记录锁等待时长 p50/p95 与锁内执行时长，判断扫描/批处理时前台查询排队的程度。
- 任务调度：自动任务触发原因、是否被合并/延迟、实际启动和完成时间，以及失败阶段。

**日志要求**

- 诊断数据不写入书名、Cookie、完整本地路径等敏感内容；路径可用源 ID 或匿名化标识。
- 发布版本使用低开销汇总或受控诊断开关，避免每个文件输出一条日志。
- 先在 Android 真机和 Windows 桌面分别用 Profile/Release 构建记录代表性用例，形成优化前基线；Debug 数据只用于功能调试。
- 优先使用现有 Flutter DevTools/性能时间线。若不足以区分数据库锁等待或扫描子阶段，再提出最小化诊断埋点；该类源码改动需在用户授权生产代码工作后实施。

### 阶段 1：先修正确性，再削减重复工作和数据库往返

#### 1A. 同一书源的索引刷新使用 single-flight 合并

为每个源 ID 维护正在执行的索引刷新任务，避免自动快照刷新和用户手动重建同时扫描同一书源。

- 普通刷新遇到正在执行的普通刷新时，共享该 Future，调用方等待同一结果。
- 普通刷新遇到强制重建时，可以等待强制重建结果。
- 强制重建遇到普通刷新时，不应直接把强制要求当作已满足：普通刷新结束后再排入一次强制重建；多个排队的强制请求可以合并为一次。
- 只有完整扫描和数据库提交成功后才发布新索引；取消或失败时保留上一次有效索引，不把部分扫描误当成删除结果。
- 清理 in-flight 状态必须放在 `finally`，并保留可诊断的错误结果。

**验收重点：** 不重复遍历同一源、不漏掉排队的强制刷新、不发布部分索引。

#### 1B. 精确 dirty、保留运行中意图，并明确同步结果

用目录/索引专用变更信号替代对所有 `LibraryStore` 通知的监听，并按源维护 dirty generation 或等价序号。

- 每次相关变更都增加 generation，即使维护周期正在运行也不能直接丢弃；同时记录源 ID 和变更原因，便于合并。
- 每个周期开始时捕获已处理的 generation；周期 `finally` 后比较当前 generation。若期间又有变化，保留 pending 状态并启动合并后的后续周期。
- 周期运行时收到新的自动化触发，应将其并入 pending intent，而不是只返回 `lastRun`。需要等待完成的调用方应能等待包含该意图的周期结果；定时器等 fire-and-forget 调用则只负责排队。
- 区分由协调器自己重载/更新数据造成的通知与外部目录变更，避免精确 dirty 修复后由周期自身通知造成无限重跑。
- 防抖只用于合并短时间内的变更，不得清除正在执行期间产生的 generation。

同步 API 当前向 UI/协调器返回状态字符串，不能作为跳过索引刷新的可靠类型化依据。建议新增结构化 `SyncOutcome`，至少表达是否成功、是否真正执行同步、应用到本地的变更域/条目、能确定失效的源 ID（无法确定时标记 unknown）、失败/未配置/限流等状态；界面文案由该结果派生。

- 本地目录变化与远端同步变化必须分别建模。远端 revision 未变只能说明本轮远端快速检查可跳过同步，不能推出本地文件夹未变。
- 按源记录最近一次成功索引对应的输入 generation/更新时间；已知本地 dirty 或同步应用了相关远端数据时推进该源的失效 generation。只有已知失效 generation 已被成功索引覆盖且 freshness 未超期，才可按缓存命中跳过刷新。
- 本地目录若没有可靠文件系统变更通知，就保留明确的 freshness 策略（例如周期复核、打开当前源时或用户强制刷新），因为外部文件改动在下次扫描前不可知；远端无变化不能取消该策略要求的本地扫描。
- 只有当同步结果明确指出它应用了会使某些远端源快照/索引失效的数据域时，才按源刷新这些快照。同步结果未知、来源状态不确定时采用保守刷新。
- 对同步前后刷新分别说明目的。通过 generation 和类型化 outcome 判断必要的源集合；若本地 dirty 在同步期间新增，周期结束后必须再处理它。

**预期收益：** 不再因无关 UI 通知启动维护；不丢失运行期间的本地变化；只跳过有可靠证据可跳过的刷新。

#### 1C. 批量标签改为可等待、分阶段、有界批次的操作

将 `batchTag` 改为可等待并返回类型化结果的任务，至少区分索引补录、内存关联更新、SQLite 持久化三个阶段。

1. 先构造不可变操作计划，去重目标并保存每项目标类型、路径、名称和父路径；目录仍是目录条目，文件仍是文件条目。
2. 对索引补录使用 `dbEnsureIndexEntries`，但按 Profile 得到的锁时长/条目规模拆成有界批次，而不是对 1000 个目标无条件持有一个大事务。每批成功后在安全边界允许前台工作插入；失败记录已完成批次，重试必须幂等。
3. 给 `TagRepository` 增加批量内存关联入口，沿用去重及 author/genre/series 语义；一批只向监听者通知一次或按阶段通知，不逐目标触发 UI 重建。
4. 为本次变更涉及的元数据标签、标签实体和关联关系提供批量数据库入口或等效的批量 diff 写入，避免仅优化索引后 `saveToSqlite()` 仍逐 tag/逐关系调用 API。按有界短事务提交，逐批记录结果；不要将缩短总耗时建立在延长单次数据库锁占用上。该专用路径必须与现有保存队列协调，并保留当前 JSON 导出备份语义，不能遗漏 `m.tags` 的持久化。
5. 新批量任务需获得本次 SQLite 保存的明确结果。不能把 `saveToDisk()` 的 Future 正常完成视作成功，因为现有实现会吞下保存异常并记录 `lastSaveError`。JSON 备份的 best-effort 结果与 SQLite 数据成功分开表达。
6. 保持现有“索引补录失败不阻断内存标签更新”的用户行为，除非后续确认要改变；但在结果中分别报告索引失败、关系持久化失败和完整成功，并允许对失败的幂等阶段重试。
7. UI 采用阶段进度和最终摘要：显示已处理/总数与成功、跳过、失败数；不为每个目标触发 UI 更新。结束摘要只有在本次 SQLite 关联持久化成功后才可报告持久化成功。

**预期收益：** 减少 N 次索引调用和逐关系数据库往返，同时避免单个超大事务造成长时间全局锁等待，并让部分成功可见、可重试。

#### 1D. 测量确认后先修扫描算法，再评估 isolate

如果 Profile 显示 Dart CPU/对象处理显著，先针对未变化子树逐次筛选 `previous` 条目的成本做算法验证。候选是扫描前一次性构建目录到条目的映射，或用有序路径索引按前缀取得子树条目；要求保留原增量判定和索引结果。

这一优化应先于移出 isolate。若 CPU 时间并不集中在旧条目筛选，不做无证据的算法改写，继续看实际热点。

### 阶段 2：前台忙碌时自动任务让路

引入一个轻量的前台工作协调器或等价机制，暂不做通用任务框架。

**不可任意延后的工作**

- 用户明确发起的扫描、同步和批量操作。
- 用户当前目录/阅读页面打开所需的必要查询，以及短小的前台交互查询。
- 已提交数据的必要持久化，以及保证数据一致性的必要恢复工作。
- H1 EH Daily 与 115 自动化不接入此协调器；它们已有独立调度、跨进程去重和持久化契约，本轮不得改变这些契约。

**前台等待反馈：云端书源扫码与 Cookie 连接**

- 用户点击添加/连接夸克、115 等云端书源后，立即在当前操作区域显示转圈和简短状态，例如“正在连接”“正在验证 Cookie”“正在读取目录”。若底层 API 能提供真实阶段，则按阶段更新；没有阶段数据时只显示 indeterminate spinner，不伪造百分比。
- 等待状态覆盖扫码等待、Cookie 提交/验证、会话建立，以及添加流程必需的首次目录读取；直到对应异步操作完成或失败才清除。
- 操作进行中禁用重复提交入口，避免用户因无反馈而重复扫码、添加或创建连接。UI 状态绑定本次 Future/操作 ID，避免旧请求结束时关闭新请求的转圈状态。
- 成功后进入原有的书源添加/目录浏览结果；失败时关闭转圈并显示可操作的错误与重试入口，不能留下永久 loading 状态。
- 这是等待可见性和重复提交保护，不代表网络耗时会缩短。该用户主动操作属于前台高优先级任务，不进入后台延迟队列。

**允许延后的工作**

- 常规自动目录索引刷新、常规抓取、非紧急清理和与当前页面无关的源预热。
- 后台任务启动前检查前台工作状态；若忙，则合并成 pending intent。相同源/类型只保留最新有效需求，全局清理只排队一次；任务原因和 freshness 期限仍要保留。
- 当前台工作结束后先留一个短暂安静窗口，再按优先级处理待办。长任务在源边界/批次边界让出调度机会；已进入的 SQLite 事务不强行中断。
- 为避免无限饥饿，为后台任务设置最大等待期限/aging。超时后允许它以很小的有界工作片段获得服务；片段之间立刻检查前台队列，必要前台工作可优先开始。片段大小应由锁等待和前台延迟基线决定，不能采用未测量的长事务。
- 前台持续活跃时，后台只在安全边界逐片执行；不能因为用户长时间阅读就永久丢弃索引维护，也不能因此阻塞当前内容打开。
- 后台失败使用有限退避并保留待处理意图，避免轮询和 dirty 事件持续重试。

**调度优先级草案**

| 优先级 | 工作 | 规则 |
| --- | --- | --- |
| 最高 | 当前目录/阅读页面打开所需的短查询、必要恢复和已提交数据持久化 | 快速启动；后台只能在事务/工作片段边界让路 |
| 高 | 用户明确发起的扫描、同步、批量操作 | 显示阶段进度；可与同源请求合并，但不能丢强制刷新意图 |
| 普通 | 当前页面相关的封面/页面加载 | 保持已有并发上限；根据前台延迟数据再考虑动态调节 |
| 低 | 常规索引刷新、抓取、清理、非紧急预热 | 可延后和合并；等待过久后获得有界服务片段 |

**远端扫描进度轮询**

当前部分远端扫描状态以约 500 ms 间隔轮询。只有 Profile/数据库数据证明该轮询造成明显锁压力时才调整；不能仅凭轮询频率推断它是瓶颈。若确有压力，可降低应用不活跃时的非可见轮询频率，并在已知状态变化时立即刷新。用户正在等待且进度可见时保持及时更新。

### 阶段 3：暂不批准；将来需单独基于证据审阅

当前不实施 isolate 扫描器、通用任务框架、全面动态并发或数据库架构重构。只有阶段 0–2 完成后，Profile 数据仍显示主 isolate 的 Dart CPU 工作直接造成前台帧超时，并且阶段 1D 的数据结构/算法检查不能经济地解决问题，才单独提交设计和审批。

届时才评估的候选做法：

- isolate 接收可序列化的根目录和扫描选项，执行遍历、路径规范化及哈希，返回普通数据对象列表。
- SQLite/FFI 写入仍由既有服务负责，使用经锁等待基线确定的有界事务；不从 worker isolate 直接共享 Rust 数据库连接。
- 为 Android 与 Windows 分别核对路径、权限、取消和错误传递；Web 或其他不支持同等 isolate 路径的平台需要兼容实现。
- 结果较大时评估内存峰值与分块返回；不能只优化帧率而显著增加内存或让扫描结果无法原子发布。

若测量显示瓶颈主要是全局 SQLite 锁，而不是主 isolate，下一步应先缩短持锁时间、减少调用数和拆分非必要写入；单纯移到 isolate 不会消除数据库锁竞争。

AI 图像增强等可能占用 CPU/GPU 的任务也不纳入本轮；只有另有证据表明它与前台争用时，才单独审阅其调度边界。

## 5. 数据流与失败语义

```text
用户前台操作 ──> 前台工作协调 ──> 扫描/同步/批处理
                                      │
                                      ├─ 文件系统或网络阶段（不持数据库锁）
                                      ├─ 有界数据库批次（提交后可让出锁）
                                      └─ 类型化阶段结果与最终摘要

相关目录变更 ──> 源级 dirty generation ──> 周期运行中？──是──> 合并 pending intent
                         │否                                  │
                         └──安排周期 <── finally 重新核对 ─────┘

常规后台维护 ──> pending 队列 ──> 前台优先；到期后有界服务并在安全边界让路
```

- 后台任务延迟时要保留源、原因、dirty generation 和 freshness 期限；应用退出时确认哪些工作可由下一次启动重建，只有无法重建的意图才需要持久化队列。
- 目录扫描未完成或写入失败时继续展示上次成功的索引；不将未遍历到的部分条目当作已删除。
- 同步失败时保留结构化失败结果并按现有重试策略处理；不能把失败、未配置或限流当成“无变化”。
- 批量标签分别报告索引、关联更新和持久化阶段。按有界批次提交时允许明确的部分进度；失败可幂等续跑，UI 不得把内存更新误报为已持久化。
- 任务取消只在源边界、批次边界等安全点响应；已提交事务不被描述成可回滚，重试以幂等方式收敛到目标状态。
- H1 EH Daily 和 115 自动化维持其现有独立工作流，本协调器不得接管或改变它们的执行/去重/持久化状态。

## 7. 验收方式

验收应覆盖 Android 真机和 Windows 桌面。先记录原始基线，再用同一数据集、同一设备和相近运行状态对比。

### 功能正确性

- 同一书源不会并行执行重复索引扫描；普通刷新与强制重建按既定规则合并，强制重建不会被普通任务吞掉。
- 周期运行期间新增的相关 dirty generation 在 `finally` 后仍会被处理；同一批自身通知不会形成无限重跑。
- 远端无变化不会被当成本地目录无变化；同步应用变化时失效的索引最终更新完整，结果不确定时按保守策略刷新。
- 自动维护可延后但不丢意图；最大等待到期后获得有界工作片段，必要前台工作在安全边界可优先执行。
- 已提交数据持久化、当前内容打开所需查询和必要恢复不会被普通后台维护策略延后；H1 EH Daily/115 自动化行为不变。
- 夸克、115 等云端书源扫码/Cookie 连接操作开始后立即显示等待转圈和真实阶段状态；等待中不能重复提交，成功/失败后都能正确结束 loading。
- 批量标签保留文件/目录类型、父路径、去重和 author/genre/series 行为，逐阶段准确报告部分失败；SQLite 保存结果能够代表本次操作，而不是只读取可能被并发保存覆盖的全局错误字段。
- 批量索引及关系写入使用有界事务；降低批量总耗时的同时，前台数据库锁等待 p95 和当前内容打开延迟不得恶化。

### 性能指标

- Android 真机和 Windows 桌面使用 Profile/Release 构建，对比设备帧预算超时数量、build/raster p95、当前源打开/操作响应时间；不以 Debug 帧数据作性能结论。
- 记录数据库锁等待 p95、锁内事务时长、扫描次数和同源重叠次数，确认没有用更长的大事务换取更短的批量总耗时。
- 批量标签在 100/1000 目标下比较总耗时、FFI 调用数、分批提交时长、锁等待、帧超时和最终数据关系。
- 云端书源连接记录端到端耗时和阶段耗时；等待动画在异步操作开始时出现，不因后台维护排队延迟，不在请求完成后残留。
- 比较各个触发原因的快照刷新次数，并覆盖本地变更/远端无变化、远端变更/本地无变化、两者同时变化及任一结果未知的场景。
- 阶段 0 后再定数值门槛。目标是帧超时与交互等待有可测改善，同时锁等待 p95 不恶化、后台没有长期饥饿、任务和数据完整性不退化；不预设无基线支持的绝对毫秒目标。

### 计划中的验证（此轮尚未执行）

- 单元测试：运行中新增 dirty、周期 finally 补跑、触发合并与等待语义、single-flight 强制刷新规则、pending aging/分片让路。
- 同步测试：本地目录变化与远端变化分别为 true/false/unknown 的组合，以及同步失败/限流/未配置时不能误标成无变化。
- 批量测试：文件与目录条目类型和父链、去重、author/genre/series 行为、合并通知、有界批次、各阶段失败与幂等重试、保存结果对应本次操作。
- 云端连接 UI 测试：操作开始时显示转圈、重复点击被阻止、旧请求不会清除新请求状态，成功与失败都会正确结束 loading 并展示对应结果。
- 数据库/集成测试：失败时继续保留上一次完整索引；必要查询与已提交数据保存不被后台延迟队列拦截。
- 回归测试：H1 EH Daily 与 115 自动化的每日触发、跨进程去重和状态持久化契约未变化。
- 性能验证：Android 与 Windows 的扫描、同步、批量标签场景分别采集 Profile/Release 帧、数据库等待和阶段指标。

## 8. 风险与应对

- **调度状态竞态：** 用显式任务状态和 `finally` 清理运行标记；覆盖前台任务启动在后台任务运行中、强制刷新排队等时序。
- **dirty 意图遗漏：** dirty generation 在周期运行期间也递增，`finally` 做版本核对并安排后续周期；测试覆盖变更恰好发生在扫描、同步、保存和周期退出边界。
- **过度合并：** 区分增量刷新与强制重建，并给每种任务定义合并规则。
- **无变化判断错误：** 远端同步结果与本地目录 dirty/freshness 分开表示；状态未知时不跳过必要刷新。
- **全局锁仍然造成排队：** 阶段 0 记录等待 p95 和事务时长；不在事务内做 I/O；批量操作分段并在事务边界让路。
- **前台持续活跃导致后台饥饿：** 设置可审阅的最大等待期限和 aging 后的有界服务片段，同时允许必要前台任务在边界优先执行。
- **用户看不到任务进度/部分成功：** 前台长任务显示阶段进度和可等待最终结果；后台延迟任务保留待办状态；失败摘要区分索引、关联和 SQLite 持久化。
- **保存错误被误报成功：** 为批量调用提供本次操作关联的保存结果，不把全局 `lastSaveError` 或 `Future<void>` 完成状态单独当作成功凭据。
- **跨平台差异：** 本轮不做 isolate；Profile 和行为测试在 Android 与 Windows 分别执行，另验证平台文件路径及存储权限不变。
- **无关自动化被调度器接管：** H1 EH Daily 和 115 自动化继续使用独立实现，不进入本次 coordinator，也不改变其去重和状态契约。

## 9. 审阅结论与实施门禁

审阅决定如下，后续方案按此口径执行：

1. **采用方案 B。** 首轮包含 P0 基线、P1 正确性与往返优化、P2 前后台让路；阶段 3 isolate 暂不批准，必须由后续性能证据单独审批。
2. **有条件延后后台维护。** 常规自动索引刷新、抓取、非紧急清理可以延后。用户主动任务、已提交数据持久化、必要恢复和当前内容打开所需查询不能被普通维护队列拦住。
3. **优先当前内容与短查询。** 当前目录、当前阅读页面和必要短查询优先；其他源维护可以等待，但必须有最大等待/aging 与有界服务片段，不能无限饥饿。
4. **有条件调整轮询。** 只有 Profile/数据库证据证明轮询造成压力才调整；后台非可见轮询可以降频，前台正在显示的进度保持及时。
5. **批量标签 UI。** 展示阶段进度和最终摘要：已处理/总数、成功/跳过/失败；不逐个目标刷新 UI。
6. **云端书源等待反馈。** 夸克、115 等扫码、Cookie 验证和连接等待显示转圈及真实阶段文案；请求期间防止重复提交，结束后按成功/失败清理状态。
